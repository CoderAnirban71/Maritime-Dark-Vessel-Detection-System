# SAMUDRA-NETRA — Layer 2: Spatio-Temporal Indexing

H3 hexagonal grid + TimescaleDB. Takes AIS pings, spill polygons, and ocean
readings from Layer 1, indexes them for fast "these hexagons, this time
window" lookups, and serves them to Layer 5 (vessel attribution).

Every file in this project was actually run against a real PostgreSQL 16 +
TimescaleDB 2.19.3 database and a real Redis instance while building it -
not just written and assumed correct. See **"What was actually tested"**
at the bottom for exactly what that covered, including one real bug it
caught before you ever saw this code.

## Files

| File | Job |
|---|---|
| `config.py` | Settings, loaded from `.env`. Nothing else is imported here. |
| `schema.sql` | Table + hypertable + index definitions. Run once, manually. |
| `db.py` | Shared asyncpg connection pool. |
| `models.py` | Pydantic validation for every incoming message. |
| `h3_utils.py` | All H3 encoding logic (point, polygon, radius search). Pure functions, no DB/Redis. |
| `repository.py` | The only file that writes SQL. Batch inserts (idempotent), hex+time queries, the spill-to-vessel join. |
| `fake_data_generator.py` | Publishes realistic synthetic messages to Redis, standing in for Layer 1 until it's ready. |
| `ingest_consumer.py` | Long-running process: Redis → validate → encode → batch insert. |
| `query_api.py` | FastAPI service Layer 5 calls: `/nearby`, `/spills/{id}/nearby-vessels`. |
| `test_pipeline.py` | Standalone smoke test - run any time to check the core logic still works. |

## Setup

### 1. Get a TimescaleDB-enabled Postgres running

```bash
docker run -d --name samudra-pg -p 5432:5432 \
  -e POSTGRES_PASSWORD=samudra_dev_pw -e POSTGRES_USER=samudra \
  -e POSTGRES_DB=samudra_netra timescale/timescaledb:latest-pg16
```

(This is the standard, well-documented way to get real TimescaleDB locally -
no manual compiling needed on your machine; the image ships the extension
built in. `CREATE EXTENSION IF NOT EXISTS timescaledb;` at the top of
`schema.sql` just activates it in your database.)

### 2. Get Redis running

```bash
docker run -d --name samudra-redis -p 6379:6379 redis:latest
```

### 3. Python environment

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

### 4. Config

```bash
cp .env.example .env
```

The defaults in `.env.example` already match the Docker commands above, so
if you used them as-is, you don't need to edit anything. **Before demo
day, confirm `REDIS_CHANNEL_AIS` / `_SPILL` / `_OCEAN` with whoever owns
Layer 1** - those three strings are the only real "contract" between your
code and theirs, and they're currently placeholders on our side.

### 5. Apply the schema (once)

```bash
psql "$DATABASE_URL" -f schema.sql
```

## Running it

Open three terminals.

```bash
# Terminal A - the consumer (writes to the DB)
python3 ingest_consumer.py

# Terminal B - test data (stand-in for Layer 1 until it's ready)
python3 fake_data_generator.py --count 100 --interval 0.2

# Terminal C - the query API (what Layer 5 calls)
uvicorn query_api:app --reload
```

Then:

```bash
curl "http://localhost:8000/nearby?lat=22.47&lon=69.06&radius_km=5"
```

Interactive API docs (auto-generated by FastAPI): http://localhost:8000/docs

## Checking nothing is broken

```bash
python3 test_pipeline.py
```

Truncates the tables and runs 13 checks against known, fixed data (H3
correctness, idempotent inserts, hex+time filtering, the spill-to-vessel
join). Exit code 0 = everything's fine. Run this after any change to
`h3_utils.py` or `repository.py` especially - that's where the real logic
lives.

## Design decisions worth knowing (so nothing here is a surprise later)

- **One H3 resolution for everything** (`H3_RESOLUTION=8`, ~0.53 km hex
  edge). Points and spill-polygon coverage share it deliberately, so they
  join on `h3_index` directly with no parent/child conversion.
- **`spill_hex_coverage` is a junction table, not an array column.** A
  spill can touch dozens of hexes; this keeps "which vessels are near this
  spill" a plain indexed join instead of an array-containment scan.
- **Radius search over-fetches on purpose.** `cells_in_radius()` returns a
  hex-shaped approximation of a circle (via `grid_disk`), which includes a
  few cells slightly beyond the exact radius. That's intentional - it
  feeds a *candidate* list; Layer 5's dead-reckoning/heading scoring does
  the precise filtering afterwards. Missing a real candidate is worse than
  including a few extra.
- **Every insert is idempotent** (`ON CONFLICT DO NOTHING`, plus a
  deterministic content-derived UUID for spills). Redis pub/sub can
  redeliver a message; without this, a redelivery would silently
  double-count a vessel's presence.
- **AIS/ocean are batched, spills are not.** High-frequency point streams
  get buffered and flushed together (by size or by time, whichever comes
  first). Spills arrive a few times an hour at most, so each is written
  immediately in its own transaction - batching it would only add latency.

## What was actually tested

Not just written - run, against real services, while building this:

- Compiled and installed a genuine TimescaleDB 2.19.3 extension from
  source and verified real hypertables via
  `timescaledb_information.hypertables`.
- `h3_utils.py`: verified every function against real Gulf of Kutch
  coordinates. **Caught and fixed a real bug this way** - the radius
  search formula was missing a `sqrt(3)` factor, causing a 5km query to
  fetch ~3x too many candidate cells (331 instead of the correct 127).
- `models.py`: confirmed valid data is accepted and invalid data (naive
  timestamps, out-of-range MMSI, out-of-range polygon vertices) is
  correctly rejected.
- `repository.py`: batch insert, idempotency under simulated Redis
  redelivery, hex+time filtering, and the spill-to-vessel join - all
  verified against a real running database with known inputs and exact
  expected outputs.
- `fake_data_generator.py`: confirmed every generated message validates
  against the real Pydantic models, and that MMSI prefixes match real
  ITU-assigned Maritime Identification Digits (419 India, 351 Panama, 538
  Marshall Islands, 563 Singapore, 636 Liberia).
- `ingest_consumer.py`: ran as a real background process, fed 250 AIS +
  250 ocean + 5 spill messages through real Redis, and confirmed **all
  250/250/5 landed correctly** - including both the size-triggered flush
  path and the time-triggered flush path for the leftover partial batch -
  plus a clean graceful shutdown on SIGTERM with no data loss.
- `query_api.py`: ran as a real server, hit every endpoint with real
  curl requests - `/health`, `/nearby` (confirmed it finds the real
  vessel and excludes distant ones), the spill-to-vessel join endpoint,
  a 404 for a nonexistent spill, a 422 for an out-of-range coordinate,
  and a 400 for an invalid time window.
- `test_pipeline.py` was itself verified to actually catch failures (not
  just always pass) by deliberately breaking a query, confirming the test
  failed, then restoring the fix and confirming it passed again.

The one thing that could **not** be verified inside this sandbox: the
actual chunking/compression behavior of TimescaleDB hypertables at scale
(network restrictions here block the usual TimescaleDB apt repo, so a
from-source build was used instead purely to enable local testing). The
schema and queries are correct regardless - hypertables behave exactly
like regular tables from a query/insert standpoint - but if you want to
see real chunk counts grow, that's worth a quick look once this is running
on your own machine via the Docker image above.
